# PRD — Sistema ficticio de Agendamiento de Citas

**Versión:** 1.0 · **Uso:** laboratorio FCV · **Fuente de especificación:** este PRD + restricciones técnicas + modelo de datos de referencia.

## 1. Objetivo

Construir una aplicación web completa de agendamiento de citas para practicar desarrollo asistido por agentes, Spec-Driven Development, verificación automatizada, ciclos autónomos y automatizaciones n8n, sin sistemas, profesionales, pacientes, credenciales o datos privados reales de FCV.

## 2. Actores

- **USER:** paciente ficticio que puede registrarse por sí mismo.
- **PROFESSIONAL:** creado por ADMIN; puede pertenecer a varias especialidades y trabajar en una o ambas sedes; gestiona disponibilidad y consulta agenda.
- **ADMIN:** administra profesionales, catálogos configurables, solicitudes especializadas y reprogramaciones.

## 3. Sedes fijas

1. Hospital Internacional de Colombia (HIC) — Km 7 Autopista Bucaramanga–Piedecuesta, Valle de Menzulí, Santander.
2. Fundación Cardiovascular de Colombia / Instituto Cardiovascular (ICV) — Calle 155A No. 23-58, Urbanización El Bosque, Floridablanca, Santander.

Estas sedes son catálogo fijo del laboratorio.

## 4. Alcance funcional

- **RF-01 Registro:** USER se registra con nombres, apellidos, tipo/número de documento, email, teléfono y contraseña. Email y documento son únicos; passwords no se almacenan en texto plano.
- **RF-02 Sesión:** login por email/contraseña, access token corto y refresh token, refresh/logout y roles en autorización.
- **RF-03 Recuperación:** token temporal de un solo uso. En desarrollo, el envío real es opcional y puede exponerse de forma segura en log/respuesta controlada. Cambiar contraseña consume/invalida el token.
- **RF-04 Perfil:** USER consulta/actualiza perfil y asocia EPS/plan/régimen mediante afiliación sin duplicarlos.
- **RF-05 Catálogos fijos:** roles, estados de cita, estados de reprogramación, regímenes y sedes, precargados y de solo lectura.
- **RF-06 Catálogos configurables:** ADMIN gestiona EPS, planes y especialidades. No hay borrado físico de catálogos referenciados; usar activación/desactivación cuando aplique.
- **RF-07 Profesionales:** ADMIN crea PROFESSIONAL, registra código/matrícula ficticia, asigna especialidades (una primaria), sedes y activación.
- **RF-08 Agenda:** PROFESSIONAL crea bloques por día/sede, edita/elimina bloques futuros sin citas comprometidas y consulta calendario. No hay bloques pasados, solapados ni en sedes no asignadas; cada bloque se discretiza en slots de 30 min.
- **RF-09 Duración:** especialidad de 30 o 60 min: uno o dos slots consecutivos. El profesional no la modifica.
- **RF-10 Disponibilidad:** USER filtra por sede, tipo general/especializada, especialidad, profesional y fecha; solo se muestran franjas que cubran toda duración.
- **RF-11 Cita general:** se elige Medicina General y un profesional general disponible. Si persiste disponibilidad al confirmar, se crea `APPROVED` automáticamente.
- **RF-12 Cita especializada:** USER selecciona especialidad, sede, profesional y horario. Nace `REQUESTED`, retiene horario y ADMIN aprueba o rechaza con motivo; el rechazo libera slots.
- **RF-13 Mis citas:** filtros por estado/fecha y visualización de sede, profesional, especialidad, fecha/hora, duración, estado y motivo de rechazo.
- **RF-14 Cancelación:** USER cancela cita futura no terminal; `CANCELLED` libera slots, no se reactiva directamente y deja historial.
- **RF-15 Reprogramación:** solo cita `APPROVED` y futura. Conserva profesional/especialidad; nueva franja queda retenida en `PENDING` sin destruir la original. ADMIN aprueba o rechaza con motivo: aprobación libera antigua/asigna nueva; rechazo libera provisional y conserva original.
- **RF-16 Agenda visible:** PROFESSIONAL consulta sus `APPROVED` por día/semana/sede y no accede a datos de usuarios fuera de sus citas.
- **RF-17 Cierre:** PROFESSIONAL marca cita pasada/aplicable como `COMPLETED` o `NO_SHOW`, con historial.
- **RF-18 Bandeja ADMIN:** ve especializadas `REQUESTED` y reprogramaciones `PENDING`, con filtros.
- **RF-19 Auditoría:** todo estado registra cita, estado nuevo, actor si existe, fuente `SYSTEM`/`USER`/`ADMIN`, fecha/hora y motivo opcional.
- **RF-20 REST:** frontend consume directamente REST Spring Boot; no hay Express/BFF y el contrato se documenta durante el proyecto.

## 5. Reglas esenciales

RN-01 no hay slots duplicados; RN-02 generales se aprueban automáticamente; RN-03 especializadas requieren ADMIN; RN-04 rechazo exige motivo; RN-05 60 min requiere slots consecutivos; RN-06 no hay citas/bloques pasados; RN-07 profesional solo publica en sedes asignadas; RN-08 especialidad activa y asignada al profesional; RN-09 cancelar/rechazar libera reservas; RN-10 reprogramación no destruye cita hasta aprobarse; RN-11 transiciones explícitas/verificables; RN-12 auditoría no es CRUD normal.

## 6. Pantallas obligatorias

Registro; login; recuperación/cambio de contraseña; home USER; búsqueda/disponibilidad; solicitar cita; mis citas/detalle; reprogramación; dashboard PROFESSIONAL; bloques/calendario; agenda profesional; dashboard ADMIN; aprobar/rechazar citas y reprogramaciones; CRUD de profesionales, especialidades, EPS y planes.

## 7. Datos

BD diseñada/explicada hasta 3FN. El modelo de referencia puede mostrarse posteriormente.

## 8. Seguridad mínima

Hash adaptativo BCrypt/Argon2 compatible con Spring Security; secretos solo por variables de entorno; JWT access/refresh separados; autorización por rol/ownership; CORS explícito; validación server-side; sin datos reales de pacientes/profesionales FCV; sin logging de passwords/tokens.

## 9. Fuera de alcance

Historia clínica, facturación/pagos reales, diagnósticos/tratamientos, datos reales FCV, integraciones clínicas, CI/CD obligatorio, SMS/WhatsApp y SMTP obligatorio.

## 10. Automatización posterior

S5/S6 añaden n8n sin cambiar núcleo: recordatorios Gmail, notificaciones de cambio por webhook + Gmail y resumen operativo diario por sede/estado.
